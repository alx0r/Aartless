§1

Executive Summary

Forever Format v1.2 (Erebus) established the foundation: a semantic, citable, AI-readable single-file HTML protocol. v1.3 is the control layer — it does not replace that foundation, it governs it.

v1.3 adapts Skiff's end-to-end encryption architecture into a self-contained, server-less document model; introduces a formal policy engine for AI inference, memory, and action; and hardens the format for mobile and offline field use. The result is a document that can be public, password-protected, shared with named collaborators, or distributed via a self-decrypting link — all without a backend, an account, or a vendor in the loop.

01 Sovereign by default

The user owns the document, the keys, the memory, the export path, and the intelligence policy.

02 Intelligent but governed

AI assistance is scoped, inspectable, revocable, and exportable at every layer.

03 Mobile, modular, interoperable

Works as a local-first document, a mobile workspace, and a networked environment builder.

§2

Context

v1.2 shipped the semantic core: section taxonomy, YAML + JSON-LD metadata, mandatory reflexive disclosure, and citation tooling. It answered how documents are structured. v1.3 answers a harder question — who controls them once they leave your hands.

The center of gravity shifts from pretty, structured output to control, trust, portability, and intelligence governance. Encryption, identity, inference, sync, and user-owned memory become first-class primitives rather than add-ons bolted on after the leaks start.

§3

Core Principles

Five commitments that every architectural decision in this document is judged against.

1 · Sovereign by default

Self-host, export in open formats, revoke access cleanly, inspect provenance, choose whether AI is local, remote, or disabled. No vendor dependency required for a document to remain usable.

2 · Encryption-native, not bolted on

Every document can exist in plaintext, password-encrypted, or fully E2EE-shared states. Encryption is a document property, not a feature flag.

3 · Mobile-first, offline-first

A single .html file, comfortably under 150KB with crypto libraries inlined, that works in any modern mobile browser — Service Worker optional, not required.

4 · Rapid AI-driven generation

AI can produce a fully functional, encrypted, styled, section-populated document in one shot from a machine-readable schema.

5 · GitHub Pages / file:// ready

No build step, no server-side rendering, no back-end dependency. Open the file, or push it to a repo — both are first-class distribution paths.

Sovereignty states

Beyond encryption, v1.3 defines a formal sovereignty model describing how a document exists in the world:

Public

Open and shareable

Private

Encrypted, user-controlled

Collaborative

Shared, explicit access rules

Ephemeral

Temporary, auto-expiring

Air-gapped

Fully offline, local-only

§5

Encryption Model

Adapted from Skiff's end-to-end encryption architecture, with the server removed. The document itself becomes the unit of trust.

Key hierarchy (per document)

  • Document Session Key (SK_doc) — a 256-bit symmetric key (XSalsa20-Poly1305 via nacl.secretbox) that encrypts all document content and metadata.
  • Per-user key wraps — for each intended reader or writer, SK_doc is encrypted with that user's public Curve25519 key and stored in the document header.
  • Password-derived key — if password-protected, SK_doc is wrapped with a key derived via Argon2id, salt stored in the clear.
  • Link key — a random key generated for URL-based sharing; SK_doc is encrypted with it and the key lives only in the URL fragment. The server — if one exists at all — never sees it.

Private keys remain entirely in browser memory. Nothing is transmitted anywhere unless the user explicitly shares it.

Encryption workflow

// document encryption, browser-side, no server round-trip 1. generate random SK_doc (nacl.randomBytes(32)) 2. serialize content to JSON / HTML sections → plaintext 3. encrypt plaintext with SK_doc (nacl.secretbox, random nonce) 4. for each recipient: encrypt SK_doc with recipient's public key (nacl.box) 5. embed ciphertext + encrypted keys + nonces + salts in a <script type="application/forever+encrypted"> block 6. document remains valid HTML — decryption JS prompts for password or local identity keys, unwraps SK_doc, renders in place

Sharing & verification — Skiff-style, no server

  • Out-of-band key verification — a public signing key rendered as a BIP39 phrase, verified by voice or in person.
  • Link sharing — the #link_key fragment is never transmitted to a server. Opening the link extracts the key client-side and decrypts in place. No login, no cookies.
  • Unsharing — with no server to revoke access, unsharing means re-encrypting with a new SK_doc and redistributing to remaining collaborators. Acceptable for a single-file document model.
§6

Document States

A document exists in exactly one of four encryption states at any moment. Users can move between them client-side by re-encrypting the session key — no server required.

StateDescriptionKey management
PublicNo encryptionNo keys
Password-protectedSymmetric encryption, one password for all readersSK_doc wrapped with Argon2id-derived key; salt stored in document
E2EE sharedEncrypted to specific Curve25519 public keysSK_doc wrapped per recipient; encrypted_keys array in header
Link-sharedEncrypted with a key embedded in the URL fragmentSK_doc wrapped with link key; server (if any) stays blind

Encryption metadata extensions to the section taxonomy

v1.2's section taxonomy is unchanged. v1.3 adds encryption-aware metadata and blocks:

  • encryption: none | password | e2ee | link
  • session_key_fingerprint: SHA-256 of SK_doc, for integrity checking
  • recipients: array of public key fingerprints
  • <script id="forever-encrypted"> — the ciphertext payload
  • #signatures section — Ed25519 signatures over the document hash
  • #provenance section — prior document hashes and timestamps

Decryption is handled by a minimal inlined JS library (~20KB gzipped, tweetnacl-js + argon2-browser) so the document stays self-contained — no CDN dependency, no network call required to read an encrypted file you already hold the key for.

§7

Intelligence Governance Model

The signature innovation of v1.3: AI assistance selectable like a power tool, not smuggled in like bad office coffee.

Inference mode

Local, remote, hybrid, or off.

Memory mode

None, session-only, document-scoped, workspace-scoped, or user-approved persistent.

Model policy

Which models are permitted for which tasks.

Action policy

What AI may read, write, suggest, delete, summarize, or automate.

Transparency policy

Always show source usage, confidence, and reasoning summaries.

Review policy

Every AI-generated change can require explicit approval before commit.

The governance ladder

Every AI action on a document climbs a fixed ladder — it cannot skip a rung.

Read
AI may inspect only approved scopes.
Suggest
AI may propose changes but not commit them.
Write
AI may generate drafts into a sandbox, isolated from the canonical document.
Commit
The user approves changes into the official version.
Forget
Memory can be deleted or time-bounded, on request or automatically.
Export
The user can move all prompts, outputs, and memory out — no lock-in.

Why this matters

This turns intelligence into a governed collaborator instead of a background process that quietly expands its own permissions. Every AI-touched document should let its owner answer, in plain terms: who can read it, where the keys live, what AI can access, whether data leaves the device, and what happens if a device is lost.

§8

Rapid Environment Protocol

Where Erebus evolves from a document system into a generative workspace system. A document should be able to become an environment.

A user should be able to spin up an intelligence brief, a research dossier, an investigative notebook, a project room, a briefing pack, a field log, a client-ready report, a mobile capture space, or an ephemeral collaboration room — from the same underlying protocol.

Template-to-environment pipeline

template → workspace → variables → connected data sources → permissions → intelligence layer → export destination

AI generation schema

An AI assistant receives a JSON schema plus a user prompt, and outputs a complete, ready-to-save .html file — inlined CSS, semantic sections, metadata, and optionally an encrypted payload.

// forever-env-schema.json — machine-readable generation contract { "title": "Document Title", "sections": ["exec-summary", "context", "methodology", "findings", "analysis", "recommendations", "reflexive"], "encryption": "none | password | e2ee | link", "recipients": ["public key fingerprints, if e2ee"], "intelligence_policy": { "memory": "document-scoped", "inference": "hybrid" }, "style": "dark | light", "output": "single-file HTML, inline CSS + encryption scaffold" }

Example: "Create an encrypted intelligence brief on the energy sector in the South China Sea, shareable with my team using these public keys." The output is encrypted, wrapped per recipient, responsive, dark-mode ready, print-optimized, and self-decrypting on open.

§9

Mobile & Offline Implementation

A sovereign system that's awkward on mobile loses half the battle. The mobile layer should behave like a field instrument, not a shrunken desktop tragedy.

Single-file PWA pattern

Optional Service Worker caches the file itself and any external resources for offline use.

Responsive by default

CSS Grid + clamp() for fluid type, no frameworks.

Touch-optimized UI

Large tap targets, swipe navigation between sections, minimal chrome.

Offline decryption

All cryptography runs in the main thread or a Web Worker — zero network calls required.

Field workflows

  • Offline capture with sync queues for reconnection
  • Low-bandwidth mode and quick share links
  • Voice note ingestion; camera-to-structure capture
  • Scan / clip / annotate workflows
  • Notification-based collaboration handoff

Goal: open the file in a mobile browser, decrypt with a password, and read or edit with full fidelity — zero bars of signal.

§12

Open Decisions

The real forks in the road — settle these before M1 starts in earnest.

How much intelligence is local by default?
Leaning as much as feasible — remote inference should be an opt-in, not the default posture.
Encryption by default, or opt-in?
For a sovereign-design product, default-on with a clear, visible user choice is the stronger position.
Document-first or workspace-first?
Leaning workspace-first for v1.3, while keeping the single document canonical underneath.
Account-based collaboration, or key-based invites?
Key-based invites are the cleaner fit for a sovereignty-first model.
What is the canonical data format?
Must be locked early — unresolved. Delay here risks a format swamp downstream.
Password-only vs. identity keys as the default?
Password-based encryption is the simplest on-ramp for rapid adoption; advanced users generate keypairs later.
Partial (section-level) encryption in v1.3, or deferred?
Powerful, but adds real complexity — tentatively deferred to v1.3.1.
Do we need a minimal relay server for E2EE key exchange?
Not required for sovereignty; a small optional WebRTC signaler could improve UX without becoming a dependency.

Reflexive Statement

On mythological naming

The use of Greek mythology for phase naming is intentional but not universal — it represents a Western-centric cultural framework. Future phases may draw from other traditions (African, Indigenous, Asian, and others) as the community evolves. We're open to renaming phases if the community finds better metaphors.

On cryptographic assumptions

This spec inherits Skiff's threat model and its Western/NIST-derived cryptographic standards (Curve25519, Argon2id, Web Crypto). It assumes a modern browser, meaningful device security, and a user capable of safeguarding a recovery key. None of these assumptions are universal.

On funding and accessibility

Requiring funding for open-source infrastructure creates barriers. The goal is self-sustaining institutional partnerships while keeping all tools freely available — core functionality will never be paywalled. Accessibility funding is treated as a floor, not a ceiling, and true accessibility requires more than technical features: it requires ongoing input from disabled users and accessibility advocates.

On limitations

This protocol cannot solve misinformation or deliberately deceptive content, access inequality that requires web literacy, or power imbalances in publishing and citation. Encryption checklists cannot guarantee security — they provide a verification framework, not a substitute for professional audits, penetration testing, and independent cryptography review.

On governance

As Forever Format grows, governance structures will need to formalize. The commitment is to inclusive, democratic process — but this is still being figured out, and critique is invited.
