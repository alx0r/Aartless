Technical Brief · Forever Commerce derivative

Building Naga Wear properly, on Shopify, from commit one.

Brand foundation is settled. This document is the engineering half: the exact pipeline, theme architecture, data model, payments/logistics stack, landed-cost math, retention automation, and phased build plan for taking a 40–100 SKU launch live on Shopify — written for a team that has never shipped on the platform before.

Scope note: Brand strategy, mythology, identity system, and market positioning are treated as finalized inputs here, not re-derived. Every technical decision below (theme choice, gateway, data structure, timeline) is made in service of that brand — restraint, provenance, and a slow, considered customer journey — not a generic Shopify build.
Exec Summary

A software project that happens to sell scarves.

The storefront is treated as a version-controlled engineering deliverable, not a themed admin panel. That means Git as the single source of truth, a local dev/build loop before anything touches production, a relational data model instead of copy-pasted rich text, and a South Africa–specific commerce stack chosen on evidence, not default.

Foundation

Shopify Online Store 2.0, Dawn theme as base, GitHub as source of truth, CLI-driven local development.

Data

Metaobjects for artisan communities, fibre specs, and care guides — referenced, never duplicated, across 40–100 SKUs.

Commerce

PayFast for payments, Bob Go for courier orchestration, SARS-accurate landed-cost modelling baked into pricing.

Methodology

The development pipeline, end to end.

The team abandons the legacy pattern — buying a bloated premium theme and editing Liquid live in the browser admin — in favour of an engineering-grade loop. Every change is local, reviewed, and deployed automatically.

1

Environment setup

Install Node.js, Git, and Shopify CLI 3.x. Authenticate the local machine to the store with shopify auth login. One environment per developer, never a shared admin login.

2

GitHub as source of truth

Connect the store via Shopify's native GitHub integration. Three branches: development, staging, production. No zip uploads, ever.

3

Feature branching

Every feature (artisan bio block, materials guide, size-and-fit drawer) gets its own branch off development, named for the feature, not the developer.

4

Local dev server

shopify theme dev spins up a sandboxed preview with hot-reload. All Liquid, JSON schema, and CSS work happens here — nothing experimental touches the live theme.

5

Linting — Theme Check

Runs automatically before commit: catches deprecated Liquid tags, missing alt text, render-blocking scripts, and SEO structure violations.

6

Pull request + peer review

Semantic commit messages, PR opened against development, mandatory review before merge — even on a two-person team.

7

Staging verification

Merges to staging deploy to a password-protected staging theme for full QA — checkout flow, PayFast sandbox, mobile breakpoints — before anything reaches production.

8

Automated production deploy

Merge to production triggers Shopify's GitHub integration to publish automatically. Every deploy is a Git commit — instant rollback if checkout breaks.

git clone https://github.com/naga-wear/storefront.git cd storefront shopify theme dev --store=naga-wear.myshopify.com # edit sections/, blocks/, assets/custom.css git checkout -b feature/artisan-bio-block git add . && git commit -m "feat: add artisan community bio block" git push origin feature/artisan-bio-block # open PR into development → review → merge → staging → production
Architecture

Dawn, Online Store 2.0, and why it's the base.

Target performance: Largest Contentful Paint under 2.5s, Cumulative Layout Shift under 0.1. Dawn is Shopify's own open-source, utility-first reference theme — no bundled frameworks, no bloat, and it's the only base that won't fight the brand's restraint.

JSON templates

templates/product.json and similar files hold no markup — they're data wrappers listing which sections render, and in what order. Structure is decoupled from rendering logic entirely.

Sections & the schema tag

Markup and Liquid logic live in sections/main-product.liquid etc. Each carries a {% schema %} block defining the merchant-editable settings surfaced in the Theme Editor.

Blocks

Atomic units inside a section — title, price, weaving-origin note, collapsible care guide, add-to-cart. Marketing drags and reorders these without a developer. Balance granularity: too fine and the editor becomes unusable, too coarse and nothing is flexible.

App blocks

Third-party functionality (e.g. product reviews) is injected via App Blocks rather than hard-coded — keeps the DOM safe from uncontrolled third-party script injection.

CSS methodology

Dawn's CSS variable token system cascades brand identity through the entire storefront without a preprocessor or build step.

  • Never edit Dawn's core base.css — it breaks the upgrade path permanently.
  • Create assets/custom.css, linked in theme.liquid after base styles so it wins the cascade.
  • Redefine root variables first — --color-base-background-1 → Warm Cream, --color-base-text → Charcoal Black — to propagate brand colour across hundreds of elements at once.
  • Use specificity, not !important, for granular overrides. Reserve !important as a rare last resort.
  • Theme Editor's per-section Custom CSS field is for isolated tweaks or prototyping only — all structural styling (e.g. 44×44px minimum touch targets) lives in version control.
Relational Data Modelling

Metafields for facts, Metaobjects for shared story.

A single Chyangra Pashmina carries micron count, staple length, harvest certification, weaving region, and care instructions. Hardcoding that into rich-text descriptions breaks the moment two scarves share a source community — which, at 40–100 SKUs pulled from a handful of artisan groups, is most of them.

Metafields

Simple key-value pairs on a single resource. Right for unique, isolated data: exact garment weight, a specific SKU identifier, precise dimensions.

Metaobjects

A centralized, multi-field database table — definition (schema) plus entries (records) — linked to products via a metaobject_reference field. One edit to an entry cascades to every product referencing it.

Metaobject definitionFieldsWhy it's shared, not per-product
Artisan CommunityRegion name, altitude, weaving method, photographyOne Dolpa entry serves every scarf sourced from Dolpa — update the bio once, it cascades everywhere.
Fibre SpecificationMicron range, staple length, harvest method, GI thresholdIdentical spec across a whole batch of Chyangra Pashmina garments.
Care GuideHand-wash steps, drying, seasonal storageOne protocol per fibre type, not per SKU — reduces post-purchase support load directly.

Product-level metafields (garment dimensions, country of manufacture as a plain string) stay as simple key-value pairs. Avoid nesting a Metaobject reference inside another Metaobject — it measurably degrades Liquid render speed at scale.

South African Commerce Stack

Payments and fulfilment, chosen for this market.

Shopify Payments isn't available natively for standard South African accounts, so a third-party gateway is mandatory — meaning Shopify's own transaction fee (2.0% Basic / 1.0% Shopify plan) stacks on top of the gateway's fee regardless of choice.

GatewayFeeLocal methodsVerdict
PayFast3.5% + R2.00Cards, Instant EFT, SnapScan, Zapper, MobicredSelected. Widest local wallet coverage — SnapScan/Zapper matter for the Cape Town demographic and offset the higher base fee through conversion.
Peach Payments~3.2% (varies)Cards, EFT, Mobicred, MasterpassAlternative for high-volume, 90-second settlement — but no SnapScan/Zapper, adding checkout friction.
Yoco2.95%Cards only (online)Rejected. Lowest fee, but card-only restriction actively harms conversion.

Multi-method local checkout can lift conversion by up to 25% versus card-only. Before launch: configure PayFast's sandbox and verify 3D Secure challenges and insufficient-funds edge cases don't break the flow. Note — Shopify's native Subscription API doesn't talk to PayFast; a future subscription model (seasonal boxes) needs middleware like SubscriptionFlow.

Fulfilment — Bob Go

API integration with Bob Go (formerly uAfrica) syncs bidirectionally with Shopify.

At checkout

Volumetric weight + destination pulls live rates from The Courier Guy, Pargo, and RAM — no shipping-shock cart abandonment.

On order

Data pushes to the Bob Go dashboard; a rule engine auto-selects the most cost-effective courier by geography.

In transit

Branded waybills, automated tracking emails — the kraft-paper unboxing narrative stays intact end to end.

Landed Cost Modelling

The tax math the pricing engine has to absorb.

HS 6214.20 (woven shawls/scarves) and HS 6301.20 (blankets) both carry SARS duty. Since the de minimis rule closed in late 2024, every clothing import pays full duty and VAT regardless of parcel value — dropshipping single units direct-to-consumer is not viable; bulk wholesale import with local Cape Town inventory is the only workable model.

ComponentFormulaR1,000 FOB example
Declared FOB valueCommercial invoice priceR 1,000.00
Customs duty45% of FOB (HS 6214.20)R 450.00
Mandatory uplift10% of FOB (SARS non-SACU rule)R 100.00
Added Tax Value (ATV)FOB + uplift + dutyR 1,550.00
Import VAT15% of ATVR 232.50
Total statutory taxDuty + VATR 682.50 (≈68% of FOB)

Excludes freight, port handling, and clearing-agent fees. Import registration with SARS (RLA / DA185.4A1) is required once annual imports exceed R150,000. This number is the floor input for the Shopify pricing/margin sheet — not a rounding buffer.

Retention Architecture

Klaviyo flows — story before discount, always.

Luxury acquisition cost is high, so retention carries profitability. Flows lean on provenance and utility, never fast-fashion discount conditioning.

Welcome flow

Day 0: fibre journey + Naga mythology, no code. Day 2: hero product as a Cape Town-climate utility. Day 4–5: hallmark certification + social proof. Day 7: first — and only — incentive, so it reads as earned.

Abandoned checkout

1hr: low-pressure reminder with cart imagery. 24hr: addresses shipping/payment anxiety, surfaces PayFast trust + return policy. 48hr: time-limited incentive for fence-sitters.

Post-purchase

First-time buyers: care and storage onboarding, no immediate upsell. Repeat buyers: conditional cross-sell by purchase history, escalating into a VIP replenishment/loyalty tier.

Recommendations

Phased build plan for a team new to Shopify.

Sequenced so the team learns the platform on low-stakes work before touching checkout or payments. Each phase has a concrete exit condition — no phase starts until the previous one's exit condition is met.

Phase 0 · Weeks 1–2

Foundations & environment

Risk: Low — tooling only, nothing customer-facing
  • Shopify plan selection, store setup, staff accounts with scoped permissions.
  • Node.js, Git, Shopify CLI installed on every dev machine; GitHub repo created and connected via the native integration.
  • Branch structure (development / staging / production) and PR review rules configured in GitHub.
  • Dawn cloned as the base theme; Theme Check installed and passing on the untouched base.
Exit: a developer can run shopify theme dev locally and push a trivial change through PR → staging without manual file uploads.
Phase 1 · Weeks 2–4

Brand skin & design tokens

Risk: Low
  • Build assets/custom.css; remap Dawn's colour and typography variables to the Naga Wear palette and Cormorant Garamond / Manrope pairing.
  • Homepage, collection, and static page sections restyled — no product logic yet.
  • Mobile-first QA: 44×44px touch targets, responsive nav, reduced-motion support.
Exit: homepage and a placeholder collection page are visually on-brand at all breakpoints in staging.
Phase 2 · Weeks 4–7

Data model & product architecture

Risk: Medium — schema mistakes are costly to unwind once SKUs are loaded
  • Define Metaobjects: Artisan Community, Fibre Specification, Care Guide.
  • Define product-level metafields (dimensions, country of manufacture) and reference fields linking products to Metaobjects.
  • Build the custom main-product section with blocks for weaving origin, care guide, and specification display.
  • Populate 3–5 pilot SKUs end-to-end to validate the schema before bulk entry.
Exit: one pilot product page correctly pulls artisan bio, fibre spec, and care guide from referenced Metaobjects with zero duplicated text.
Phase 3 · Weeks 7–9

Payments & fulfilment integration

Risk: High — checkout and money movement
  • PayFast merchant account, sandbox configuration, and full checkout QA (3D Secure, insufficient funds, refund path).
  • Bob Go integration for live rate quoting and courier rule engine (Courier Guy / Pargo / RAM).
  • Branded waybill setup and tracking-email templates.
Exit: a full sandbox purchase — cart to paid to waybill generated — completes without manual intervention.
Phase 4 · Weeks 9–11

Bulk catalogue load & pricing

Risk: Medium
  • Landed-cost model (duty + uplift + VAT) applied to every SKU before retail price is set.
  • Remaining 35–95 SKUs loaded against the validated schema from Phase 2.
  • Photography and copy pass for each product page; alt text enforced by Theme Check.
Exit: full catalogue live in staging, every SKU priced against actual landed cost, zero missing alt text or broken Metaobject references.
Phase 5 · Weeks 11–13

Retention automation & launch

Risk: Medium
  • Klaviyo connected; welcome, abandoned-checkout, and post-purchase flows built and tested against real event triggers.
  • Performance audit against LCP <2.5s / CLS <0.1 targets; Theme Check run clean on the full theme.
  • Soft launch to a limited list, monitor checkout completion and courier rate accuracy, then public launch.
Exit: store is public, first real order fulfilled end-to-end, flows firing correctly on live customer events.

Repository structure

Pre-launch checklist

  • Theme Check passes clean on the full theme, zero warnings.
  • PayFast sandbox: successful payment, declined payment, 3D Secure challenge all verified.
  • Bob Go rates confirmed against at least three real South African postal codes.
  • Every product page has an Artisan Community, Fibre Specification, and Care Guide reference — none blank.
  • Landed-cost model applied to every SKU's retail price, not just a sample.
  • Mobile Lighthouse score checked on product, collection, and cart pages.
  • Klaviyo flows tested against a real (not simulated) checkout-abandonment event.
  • SARS importer registration filed if projected annual imports exceed R150,000.

Glossary

Online Store 2.0
Shopify's architecture generation that decouples page structure (JSON templates) from rendering logic (sections/blocks), enabling merchant-editable layouts without developer intervention per change.
Metaobject
A custom, relational data table in Shopify's backend, referenced by multiple products — the mechanism that lets one artisan bio serve fifty scarves.
ATV (Added Tax Value)
SARS's VAT calculation base: FOB value plus the 10% non-SACU uplift plus customs duty.
FOB
Free On Board — the declared commercial invoice value of goods before freight, insurance, duty, or VAT.
