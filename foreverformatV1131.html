Forever Format™ v1.3.1 · Unified Specification

One protocol, three parts: Core, Secure, Intelligence.

Forever Format is an open protocol for sovereign digital knowledge. It combines portable documents, end-to-end encryption, governed AI assistance, and long-term interoperability into a single self-contained object — a single .html file that carries its own structure, its own keys, and its own rules for how intelligence may touch it.

Part I
Forever Core

The canonical document model: metadata, section taxonomy, provenance, and serialization. Defines what a Forever document is.

Part II
Forever Secure

Cryptographic identity, end-to-end encryption, document states, and integrity. Defines who can read it.

Part III
Forever Intelligence

The governance ladder, memory scopes, and the Rapid Environment Protocol. Defines what AI may do with it.

§0

Abstract

This specification unifies the three-part Forever Format protocol into a single reference document. Each part was previously drafted independently — Core, Secure, and Intelligence — so that developers could implement one without depending on the others. v1.3.1 brings them together for readability without collapsing their boundaries: a compliant implementation MAY support Core alone, Core plus Secure, or the full trilogy, and MUST declare which it supports.

A Forever document is a single .html file that is human-writeable, machine-producible, and readable by any modern browser — self-contained, offline-capable, and free of server or vendor dependency. It carries a globally unique canonical identifier, an optional cryptographic identity, and an optional, inspectable AI governance policy.

MUST / MUST NOT — absolute requirement SHOULD / SHOULD NOT — strong recommendation, exceptions must be understood MAY — truly optional per RFC 2119
§0.1

Core Principles

Sovereign by default

The user owns the document, the keys, the memory, the export path, and the intelligence policy. No document should depend on a vendor to remain usable.

Encryption-native, not bolted on

Every document exists in exactly one of four defined states. Encryption is a document property, not a feature flag.

Governed intelligence

AI assistance is scoped, inspectable, revocable, and exportable at every layer — a collaborator bound by policy, not a background process.

Mobile-first, offline-first

A single file under ~150KB with crypto inlined, usable with zero bars of signal.

§0.2

Five-Layer Architecture

The three specification parts map directly onto the architecture's layers. Core defines L1; Secure defines L2; Intelligence defines L3. L4 and L5 are named here and specified in future extensions.

Part I

Forever Core

The canonical document model, metadata, section taxonomy, provenance, and serialization. Status: Draft. Depends on: nothing — Core is the base.

§1

Canonical Identifier

Every document revision MUST have a canonical identifier (CID) that is globally unique and immutable, using the forever URI scheme:

forever://document/<hash>

Where <hash> is a SHA-256 digest, lowercase hex, of the document's immutable content envelope (see §5 Provenance). The CID MUST be present in the <meta name="forever-cid"> tag, the JSON-LD block, and the YAML frontmatter as cid.

The CID is derived from the canonical serialized form of the document — excluding mutable rendering content like CSS, but including all semantic content, metadata, and provenance fields. Documents not yet finalized MAY use a temporary CID with a draft flag, but any published or citable version MUST carry a permanent one.

§2

Abstract Document Model

A Forever document consists of four parts:

Metadata

Properties describing the document — title, author, version, license, CID, and related fields.

Content

A sequence of semantically typed sections.

Provenance

References to prior revisions, and optionally signed identity (optional in Core, required in Secure).

Rendering hints

Optional CSS and structural markup — presentation only, never part of the semantic core.

All resources SHOULD be embedded to ensure long-term portability. External resources MAY be loaded for presentation only; semantic integrity must never depend on them.

§3

Section Taxonomy

A compliant document SHOULD use these standard IDs for top-level <section> elements. Additional custom sections are permitted. Sections MUST use a corresponding id attribute and SHOULD begin with an <h2> heading.

Section IDRequirementPurpose
#exec-summaryRECOMMENDEDHigh-level overview and key findings
#contextRECOMMENDEDBackground and historical framing
#methodologyOPTIONALProcess, sources, limitations
#findingsOPTIONALCore data, evidence, results
#analysisOPTIONALInterpretation, critical evaluation
#timelineOPTIONALChronology of events
#discussionOPTIONALSynthesis and implications
#recommendationsOPTIONALActionable guidance
#citationsRECOMMENDEDFormal references, BibTeX-ready
#appendixOPTIONALSupplementary material
#reflexiveREQUIREDSelf-critique, bias disclosure, ethical statement
#metaREQUIREDVersion, license, provenance, CID

#reflexive and #meta are the only two sections a compliant reader is required to validate for presence.

§4

Metadata

Forever Core uses three layers of metadata, all embedded in <head>: YAML frontmatter in an HTML comment (human-readable), JSON-LD in a <script type="application/ld+json"> (machine-readable), and <meta> tags for quick access.

Required fields

title, author, document_type, license, version, created, cid — all MUST be present in both the YAML block and the JSON-LD.

Recommended fields

updated, citation_style, tags, ai_context_tags, forever_format_version.

<!-- --- title: "My Document" author: "Contributor Name" document_type: "Research Note" license: "CC BY-NC-SA 4.0" version: "1.0.0" created: "2026-01-15" cid: "forever://document/3a4b..." tags: ["intelligence", "analysis"] forever_format_version: "1.0" --- -->

The JSON-LD MUST mirror this data using schema.org types (typically ScholarlyArticle or TechArticle), including @context, @type, name, author, version, datePublished, license, and an identifier property carrying the CID.

§5

Provenance & Versioning

Each document MUST include a provenance block recording its lineage, stored inside #meta as a structured list (and optionally mirrored in JSON-LD).

The #meta section MUST contain a <div class="provenance"> listing revisions, each with cid, version, date, author, and a change note.

If a document derives from another Forever document, #meta MUST include a <link rel="predecessor-version" href="<cid>"> tag plus a clear statement in the provenance block. The CID of a new revision is computed from its content including the new provenance entry referencing its predecessor — this creates an immutable chain.

§6

HTML Serialization

A Forever Core document is a valid HTML5 document. It MUST be usable standalone (file://) or served via HTTP, with CSS and essential scripts inlined. Sections use <section id="..."> with headings; encoding is UTF-8 throughout.

Recommended MIME type: application/vnd.forever+html. Documents MAY also be served as text/html for broad compatibility.

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>Title</title> <!-- YAML metadata --> <script type="application/ld+json">{ /* JSON-LD */ }</script> <style>/* inlined minimal styling */</style> </head> <body> <article> <section id="exec-summary"><h2>Executive Summary</h2>...</section> <section id="reflexive"><h2>Reflexive Statement</h2>...</section> <section id="meta"> <h2>Metadata</h2> <div class="provenance">...</div> </section> </article> </body> </html>
§7

Core Compliance

A reader (parser) claiming compliance MUST

Extract the CID from metadata · parse section structure by id · validate presence of #reflexive and #meta · reject documents with missing or malformed required metadata.

A writer (generator) MUST

Produce a valid HTML5 document with all required metadata · include a #reflexive section · compute and embed a permanent CID once finalized.

Forever Secure and Forever Intelligence layer on top of Core and must not violate these base requirements.

Part II

Forever Secure

Cryptographic identity, end-to-end encryption, and integrity. Status: Draft. Depends on: Forever Core v1.0.

§8

Cryptographic Primitives

All implementations MUST use the following algorithms. No other ciphers or curves are permitted within this specification — cryptographic agility is deliberately excluded to avoid downgrade attacks (see §14).

PurposeAlgorithmDetails
Public-key encryptionX25519 + XSalsa20-Poly1305NaCl crypto_box — Curve25519 ECDH, AEAD
Symmetric encryptionXSalsa20-Poly1305NaCl crypto_secretbox — authenticated encryption
Digital signaturesEd25519NaCl crypto_sign
Password key derivationArgon2idSalt: 256 bits · output: 256 bits · params: t=3, m=65536 KiB, p=2; salt stored in the clear
HashingSHA-256Fingerprints, canonical identifiers
Public-key fingerprintBIP39 (first 80 bits of SHA-256)6-word phrase for out-of-band verification

Nonces: a 192-bit random nonce MUST be generated per encryption operation and stored with the ciphertext. Nonce reuse with the same key MUST NOT occur. All randomness MUST come from a cryptographically secure source (e.g. crypto.getRandomValues).

§9

Identity Model

An agent MAY possess a Forever Identity: an X25519 encryption keypair plus an Ed25519 signing keypair.

{ "@context": "https://forever-format.org/identity/v1", "id": "forever://identity/<hash-of-signing-public-key>", "encryptionPublicKey": "<base64>", "signingPublicKey": "<base64>", "verified": false }

Private keys MUST NOT appear in any document in plaintext. They MAY be stored locally (IndexedDB, or a file) encrypted with a password-derived key.

Public key verification phrases

The signing public key SHOULD be presentable as a BIP39 mnemonic for out-of-band verification: SHA-256 the raw signing public key, truncate to 10 bytes (80 bits), encode as a 6-word BIP39 phrase. Agents SHOULD mark an identity "verified" only after this out-of-band check — voice call, in person, never over the same channel carrying the document.

§10

Document Encryption Model

Key hierarchy

  • SK_doc — random 256-bit key encrypting document content (secretbox)
  • Password-protected — SK_doc wrapped with an Argon2id-derived key, salt included
  • E2EE shared — SK_doc wrapped to each recipient's public key via crypto_box
  • Link-shared — SK_doc wrapped with a random link key (LK) embedded only in the URL fragment, never transmitted to a server

All wrapped keys are stored in the encrypted_keys metadata block.

Decryption process

  1. Determine document state from metadata
  2. Retrieve wrapped SK_doc for the current reader — or prompt for password, or extract link key from the URL fragment
  3. Unwrap SK_doc
  4. Decrypt ciphertext with SK_doc and its nonce
  5. Replace document body with decrypted content

If decryption fails, the reader MUST display an appropriate error and MUST NOT render any plaintext from the encrypted block.

§11

Document States

A document is in exactly one of four states, indicated by <meta name="forever-encryption-state">.

🔓Publicstate: none
  • No encryption; plain HTML
  • The meta tag is optional but SHOULD be present for explicit signaling
🔒Password-protectedstate: password
  • SK_doc wrapped with an Argon2id-derived key
  • Salt + params stored in the clear
  • Single encrypted_keys entry, kid: "password"
🗝️E2EE sharedstate: e2ee
  • SK_doc wrapped per recipient public key
  • Each entry carries kid, encrypted_key, sender_public_key
  • Author MAY hold a self-wrap for later access
🔗Link-sharedstate: link
  • 256-bit link key (LK) generated, appended after # in the URL
  • Server, if any, MUST NOT receive the fragment
  • Optionally augmented with expiration or view limits, enforced client-side
§12

Key Management & Sharing

Sharing (Alice → Bob, via E2EE)

  1. Retrieve Bob's public encryption key
  2. Verify Bob's identity — RECOMMENDED, via BIP39 phrase
  3. Decrypt the document's current session key
  4. Wrap a copy of SK_doc to Bob's public key
  5. Add Bob's entry to encrypted_keys
  6. Re-serialize the document
  7. If previously password-protected, Alice MAY remove that entry, converting to pure E2EE

Unsharing

With no server to enforce revocation, unsharing means: re-encrypt with a new SK_doc, wrap it to all remaining collaborators except the one being removed, and redistribute. The revoked party retains access to the content they already have, but not to future revisions.

Identity export/import

An identity SHOULD be exportable as a password-encrypted JSON file, or a paper wallet containing a BIP39 mnemonic of the private key seed.

§13

Signatures & Integrity

The CID serves as a content hash over the document's immutable core — any modification to semantic content or encryption metadata yields a different CID.

An agent MAY sign a document via a <section id="signatures"> containing one or more Ed25519 signatures, each with signer, signature (base64, over the CID), and an optional timestamp. Verifiers MUST check the signer's identity public key against the signature.

§14

Security Considerations

  • Key storage — browser localStorage/IndexedDB is not inherently XSS-safe; minimize exposure, consider Web Worker isolation.
  • Password strength — password-based encryption is only as strong as the password; applications SHOULD enforce minimum length and complexity.
  • Link sharing — a link key in the URL fragment may end up in browser history; users SHOULD be warned to transmit links over secure channels.
  • Cryptographic agility — deliberately absent. Upgrades require a new spec version, avoiding downgrade attacks at the cost of a defined migration path.
  • Timing attacks — constant-time comparisons MUST be used where feasible.
  • Randomness — a failure of the RNG compromises all security; platforms must guarantee a properly seeded CSPRNG.
Part III

Forever Intelligence

AI governance, cognitive policy, and environment generation. Status: Draft. Depends on: Forever Core v1.0, Forever Secure v1.0.

§15

The Governance Ladder

Every cognitive agent interacting with a Forever document MUST obey the ladder — six sequential, cumulative permission levels. An agent granted a given rung implicitly holds all lower rungs; higher rungs require explicit, auditable escalation. Rungs MUST NOT be skipped.

0ReadInspect content within approved scopes only. No modification, no retention beyond session.
1SuggestPropose changes — annotations, comments, suggested edits — without modifying the canonical document.
2WriteGenerate content into a sandboxed draft area. Drafts are not part of the document until committed.
3CommitAgent-originated changes may enter the canonical document, subject to review policy.
4ForgetMust be able to delete memory on request and honor time-bound retention limits.
5ExportUser may export all prompts, outputs, and memory to an open format. No data lock-in.

Policy scoping

The ladder applies at three levels — document, workspace, and user default — with document overriding workspace overriding user default. The effective policy for any action MUST be the most restrictive combination of all applicable policies.

§16

Memory Scopes

Agents MAY retain state across interactions only within an explicitly declared scope — the maximum permitted scope is set in the document's intelligence policy.

ScopeSymbolDescription
NonenoneNo state retained between interactions; every request is stateless
SessionsessionPersists for one editing/viewing session; discarded on close, logout, or timeout
Document-scopeddocumentPersists across sessions for this document only
Workspace-scopedworkspacePersists across all documents in a defined workspace
User-approved persistentpersistentPersists indefinitely, only with explicit user approval

An agent MUST discard all memory exceeding the declared scope. The user MUST be able to inspect all retained state, delete individual memories or clear everything, and export retained state as machine-readable JSON — this is what the Forget rung requires in practice.

§17

Intelligence Policy

A document MAY carry an intelligence policy in a <script type="application/forever+intelligence-policy"> block in <head>.

{ "@context": "https://forever-format.org/intelligence/v1", "governance": { "max_rung": "suggest", "require_approval_for_commit": true }, "memory": { "scope": "document", "retention_days": 30, "auto_delete_on_close": false }, "inference": { "mode": "hybrid", "allowed_models": [{ "provider": "anthropic", "model": "claude-*" }], "forbidden_models": [{ "provider": "*", "model": "*", "training_data_unknown": true }] }, "actions": { "allow_read": ["#exec-summary", "#findings"], "allow_write": ["#analysis"], "allow_suggest": true, "allow_summarize": true, "allow_auto_commit": false }, "transparency": { "show_confidence": true, "show_sources": true, "show_reasoning": true, "log_all_interactions": true }, "review": { "require_approval": "all", "approval_mode": "human" } }
Inference mode

local — on-device only · remote — cloud models permitted · hybrid — sensitive ops local, rest remote · off — no AI assistance permitted.

Model policy

allowed_models / forbidden_models constrain provider and model by name or wildcard, with optional constraints like audited or jurisdiction.

Action policy

Section-level read/write scoping, plus booleans for suggest, summarize, and auto-commit.

Review policy

require_approval: all / structural / none · approval_mode: human / threshold.

A document with inference.mode: "off" MUST NOT be processed by any cognitive agent beyond basic indexing.

§18

Transparency & Logging

Every interaction between a cognitive agent and a document MUST be logged: timestamp, agent identifier, rung exercised, scope of data accessed, actions taken, confidence scores, and sources referenced. The log SHOULD live in #meta as a <div class="ai-interaction-log"> JSON block, or reference an external append-only log, and MUST remain accessible to the user.

Generated content MUST be tagged with a confidence score, source citations where applicable, and a brief reasoning summary — visible in the rendered document and machine-readable in metadata.

§19

Rapid Environment Protocol (REP)

A declarative JSON schema enabling an AI system to generate a complete, functional Forever document in a single output.

{ "@context": "https://forever-format.org/rep/v1", "document": { "title": "string", "author": "string", "document_type": "string", "tags": [], "license": "string" }, "structure": { "sections": ["exec-summary", "findings", "reflexive", "meta"] }, "style": { "theme": "dark | light", "accent_color": "hex", "font_family": "serif | sans | mono" }, "encryption": { "mode": "none | password | e2ee | link", "recipients": [] }, "intelligence_policy": { "..." }, "output": { "format": "html", "inline_css": true, "inline_crypto": true, "standalone": true } }

An AI system receiving a REP schema and a prompt MUST produce a document that passes Core compliance, includes all requested sections populated, applies the specified styling, wraps keys correctly if E2EE is requested, and embeds the intelligence policy if provided. The output MUST be immediately openable in a browser with no post-processing.

Suggested template library: intelligence-brief · investigative-report · research-notebook · threat-assessment · field-log · meeting-minutes · project-room · briefing-pack.

§20

Environment Model

A document configured with an intelligence policy, memory scope, and section structure functions as a cognitive environment.

1Create
  • User or AI generates a document from a REP template
2Configure
  • Set the governance ladder ceiling, memory scope, inference mode
3Populate
  • Add content manually, via agent suggestions, or automated pipelines
4Interact
  • Agents operate within policy bounds; interactions are logged
5Evolve
  • Document may be revised, re-encrypted, shared, or forked
6Archive or destroy
  • Export, encrypt for long-term storage, or securely delete — including all agent memory

Multiple agents MAY interact with the same document simultaneously, each with its own policy entry via intelligence_policy.agents[]. Agent-to-agent communication MUST be logged and subject to the same ladder.

§21

Intelligence Compliance & Security

A compliant implementation MUST enforce the ladder for all agents, support and honor the full policy schema, log all interactions accessibly, tag generated content with confidence/source/reasoning, support REP generation and validation, and permit memory inspection, deletion, and export. Partial compliance MAY be claimed for policy-schema-only implementations, but limitations MUST be declared clearly.

  • Policy bypass — an agent running outside the document's execution context has limited technical enforcement; the policy MUST be treated as a binding contract, with cryptographic attestation used where possible.
  • Memory leakage — agents MUST isolate memory between documents unless workspace scope is explicitly authorized; cross-document leakage is a confidentiality violation.
  • Model integrity — a compromised model may ignore policy; implementations SHOULD verify model identity via attestation and MUST log all invocations.
  • Log integrity — interaction logs MUST be append-only and tamper-evident, MAY be cryptographically chained to the document's provenance.
Part IV

Implementation Guide

Practical, code-level guidance for building, encrypting, and governing Forever documents. Applies to all three specification parts.

§22

Quick Start

Companion libraries: tweetnacl-js (box, secretbox, sign), argon2-browser (Argon2id), bip39 (optional, verification phrases). All examples assume ES2020+.

Computing a CID (pseudocode)

async function computeCID(htmlDoc) { // 1. extract sections in canonical order // 2. sort metadata fields alphabetically // 3. serialize provenance as JSON const canonical = sortedMeta + '\n' + provStr + '\n' + content; const hash = await crypto.subtle.digest('SHA-256', encode(canonical)); return `forever://document/${toHex(hash)}`; }
§23

Encryption in Practice

Password-protected encryption

async function encryptWithPassword(htmlContent, password) { const sk = nacl.randomBytes(32); const nonce = nacl.randomBytes(nacl.secretbox.nonceLength); const ciphertext = nacl.secretbox(encode(htmlContent), nonce, sk); const salt = nacl.randomBytes(32); const derived = await argon2.hash({ pass: password, salt, time: 3, mem: 65536, parallelism: 2 }); const wrapNonce = nacl.randomBytes(nacl.secretbox.nonceLength); const wrappedSK = nacl.secretbox(sk, wrapNonce, derived.hash); // embed: forever-encryption-state, salt, params, wrapped key, ciphertext }

Decryption

async function decryptPasswordDoc(encryptedHTML, password) { // 1. read salt + params from meta tags // 2. derive key via Argon2id // 3. unwrap SK_doc with nacl.secretbox.open — throws on wrong password // 4. decrypt content ciphertext with SK_doc — throws if corrupted return decodedHTML; }

E2EE sharing

function encryptForRecipient(sk, recipientPublicKey, senderSecretKey) { const nonce = nacl.randomBytes(nacl.box.nonceLength); const encryptedKey = nacl.box(sk, nonce, recipientPublicKey, senderSecretKey); return { nonce, encryptedKey }; // → entry in encrypted_keys[] }
§24

Policy-Aware Agent Proxy

An agent implementation should check policy before any operation — never after.

class ForeverAgentProxy { constructor(documentDOM) { this.policy = JSON.parse(documentDOM.getElementById('forever-intelligence-policy').textContent); this.log = []; } canRead(sectionId) { const allowed = this.policy.actions.allow_read; return allowed.includes('*') || allowed.includes(sectionId); } suggest(sectionId, proposal) { if (!this.canRead(sectionId)) throw new Error('Read access denied'); this.log.push({ action: 'suggest', section: sectionId, timestamp: Date.now() }); } commit(change) { if (this.policy.review.approval_mode === 'human') { if (!confirm('Approve AI change?')) return; } this.log.push({ action: 'commit', change }); } }
§25

Validation Checklist

Before releasing a Forever document, verify:

  • HTML5 validity
  • All required metadata present — YAML and JSON-LD
  • #reflexive section exists and is substantive
  • #meta contains a provenance block
  • If encrypted: state metadata, encrypted keys, and content blocks present; key wrapping valid
  • CID computed, embedded, and matches recomputation
  • Intelligence policy, if present, is well-formed and internally consistent
  • Document loads and decrypts correctly in a fresh browser profile

Open Decisions

Canonical data format Resolved — Core §1–2
Single-file HTML5, semantic sections plus YAML/JSON-LD metadata, identified by a forever://document/<hash> CID.
Password-only vs. identity keys as default Resolved — Secure §11
Password is the default on-ramp; identity keypairs layer in for E2EE once a user opts in.
Cryptographic agility Resolved — Secure §14
Deliberately excluded. One fixed primitive set per spec version to avoid downgrade attacks.
How much intelligence is local by default? Open
The policy schema supports it (inference.mode: "local"), but no default is mandated by the spec — left to implementers.
Partial (section-level) encryption Open
Not defined in Secure v1.0. Powerful, but adds real complexity — deferred to a future extension.
Minimal relay server for E2EE key exchange Open
Not required for sovereignty. A small optional WebRTC signaler could improve UX without becoming a dependency.
Canonicalization algorithm for CID computation Open
Pseudocode is given (§22), but the exact deterministic algorithm — field ordering, whitespace handling, encrypted-content inclusion — needs a separate implementation note before independent implementations can interoperate.
§28

Reflexive Statement

On specification maturity

This unified draft is an improvement over its predecessor precisely because it separates vision from protocol: RFC-2119 language, explicit algorithm tables, and defined compliance criteria replace prose aspiration. It is still not a finished protocol. Version negotiation, a fully specified canonicalization algorithm, and independent interoperability testing are all outstanding — see Open Decisions.

On mythological and cryptographic framing

Earlier phase naming drew on Greek mythology — an intentional but Western-centric frame, open to revision. This spec's cryptography inherits the same lineage: Curve25519, Argon2id, and Web Crypto are NIST/Western-standard-adjacent choices. Neither framing is universal, and both are named here rather than left implicit.

On limitations

This protocol cannot solve misinformation or deliberately deceptive content, access inequality that requires web literacy, or power imbalances in publishing and citation. A security specification is a verification framework, not a guarantee — production implementations should undergo independent cryptographic review, not rely on this document alone.

On governance

Governance structures for the project itself — as distinct from the governance ladder the protocol defines for AI agents — remain unformalized. This is acknowledged rather than resolved, and critique is invited.
