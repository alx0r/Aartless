Network Monitoring Field Manual

IP Investigation & Connection Analysis for OSINT Researchers

Executive Summary

For researchers, journalists, and professionals handling sensitive information, network visibility is fundamental operational security. Every active connection represents a potential data leak, surveillance vector, or compromise indicator. This manual provides cross-platform tools to answer three critical questions:

  1. Who is my device talking to? (Active connections + remote IPs)
  2. What processes are responsible? (Process mapping + PID identification)
  3. Should I be concerned? (Threat assessment + response protocols)
Core Principle: Assume all traffic is monitored. Your operational security depends on knowing—and controlling—every network connection your device initiates.

When to Use This Manual

  • Pre-operation audit: Before handling sensitive materials, verify no unexpected connections exist
  • Anomaly detection: Investigate unfamiliar processes or connection patterns
  • Incident response: Document compromise indicators during security events
  • Baseline establishment: Create normal-state snapshots for comparison

Platform Coverage

macOS Windows Linux Android iOS

Context: Why Network Monitoring Matters

Modern operating systems maintain dozens of simultaneous network connections—background updates, telemetry, cloud sync, DNS resolution. Most are legitimate. Some are not. The challenge: distinguishing signal from noise.

The Threat Landscape

Data Exfiltration

Malware, spyware, and surveillance tools operate by establishing persistent connections to command-and-control servers. These connections often masquerade as legitimate traffic (HTTPS to cloud services). Network monitoring reveals the destination IPs, allowing verification against known-bad infrastructure or unexpected geographic locations.

Metadata Leakage

Even encrypted connections leak metadata: timing, packet sizes, connection frequency. For researchers working with sensitive sources, metadata alone can reveal operational patterns. Understanding what connects when and how often is critical tradecraft.

Supply Chain Compromise

Third-party applications increasingly phone home—sometimes to update servers, sometimes to analytics platforms, occasionally to adversary-controlled infrastructure. The 2020 SolarWinds incident demonstrated that trusted software can harbor malicious network behavior. Regular audits catch anomalies early.

Legal/Jurisdictional Risk

Connections to servers in certain jurisdictions may expose data to foreign intelligence services or legal intercept. Researchers handling materials subject to source protection need to know if their tools are contacting servers in high-risk countries.

Historical Precedent

Network forensics has uncovered:

  • NSA QUANTUM (2013): Man-in-the-middle attacks exploited unmonitored connections to inject exploits
  • Pegasus spyware (2016-present): Zero-click attacks create connections that don't appear in application logs but show in netstat
  • Stuxnet (2010): Anomalous connections to update servers revealed industrial control system compromise

Bottom line: If you can't see it, you can't secure it. Network monitoring is not paranoia—it's hygiene.

Methodology: How Network Inspection Works

Core Concepts

1. Sockets & Connections

A socket is an endpoint for network communication, defined by:

  • Protocol: TCP (connection-oriented) or UDP (connectionless)
  • Local address: Your device's IP + port
  • Remote address: Destination IP + port
  • State: ESTABLISHED, LISTEN, TIME_WAIT, etc.

2. Process Identification

Every connection is owned by a process (identified by PID). Mapping PID → process name → application reveals what is making the connection. Critical for distinguishing browser traffic from background daemons or malware.

3. Port Significance

Port Service Normal Use Suspicious If...
80 HTTP Web browsing Unencrypted traffic from secure apps
443 HTTPS Secure web/APIs Unknown process, high frequency
22 SSH Remote administration Listening without explicit enablement
53 DNS Name resolution Direct queries to non-system resolvers
445 SMB File sharing (Windows) Internet-facing, unexpected geography
1080 SOCKS Proxy tunneling Undocumented proxy usage
>1024 Ephemeral Temporary client ports N/A (normal for outbound)

4. Connection States

  • ESTABLISHED NORMAL — Active, two-way communication
  • LISTEN AUDIT — Waiting for inbound connections (potential exposure)
  • TIME_WAIT NORMAL — Recently closed, cleanup phase
  • SYN_SENT MONITOR — Attempting connection (may indicate scanning)
  • CLOSE_WAIT CHECK — Remote closed, local hasn't (possible leak)

Tools & Techniques

All platforms provide built-in utilities:

  • lsof (macOS/Linux): List open files, including network sockets
  • netstat (universal): Display network statistics and connections
  • ss (modern Linux): Faster netstat replacement
  • Get-NetTCPConnection (Windows PowerShell): Native connection query
  • tcpdump (Unix): Packet capture for deep inspection (advanced)

Operational Note: These tools require elevated privileges (sudo / Administrator) to see connections from other users' processes.

Platform Commands: Investigation Toolkit

macOS Investigation Commands

Quick Connection Snapshot

sudo lsof -iTCP -sTCP:ESTABLISHED -n -P

What it shows: All active TCP connections with process name, PID, user, and remote IP:port.

Flags explained:

  • -iTCP: TCP connections only
  • -sTCP:ESTABLISHED: Filter to established state
  • -n: Show IPs (don't resolve hostnames—faster, no DNS leakage)
  • -P: Show ports as numbers

Listening Ports (Inbound Exposure)

sudo lsof -iTCP -sTCP:LISTEN -n -P

AUDIT Any LISTEN state means your machine accepts inbound connections on that port. Verify these are intentional (SSH, file sharing, etc.).

Live Monitoring

sudo nettop -m tcp -p

Real-time per-process bandwidth + connections. Press q to quit.

Local Network Discovery

arp -a

Shows devices your machine has recently communicated with on LAN (IP ↔ MAC mappings).

Extract Remote IPs Only (Clean List)

sudo lsof -i -nP | awk '/ESTABLISHED/ {print $9}' | sed 's/.*->//' | cut -d: -f1 | sort -u

Outputs unique remote IPs for batch lookups or blocklist generation.

Full Audit Script

Save comprehensive report to file:

#!/bin/bash
OUT=~/network_report_$(date +%Y%m%d_%H%M%S).txt
{
  echo "=== MACOS NETWORK AUDIT ==="
  echo "Generated: $(date)"
  echo
  echo "=== ESTABLISHED CONNECTIONS ==="
  sudo lsof -iTCP -sTCP:ESTABLISHED -n -P
  echo
  echo "=== LISTENING PORTS ==="
  sudo lsof -iTCP -sTCP:LISTEN -n -P
  echo
  echo "=== TOP REMOTE IPs ==="
  sudo lsof -i -nP | awk '/ESTABLISHED/ {split($9,a,"->"); split(a[2],b,":"); print b[1]}' | sort | uniq -c | sort -rn | head -20
  echo
  echo "=== ARP TABLE ==="
  arp -a
} | tee "$OUT"
echo "Report: $OUT"

Make executable: chmod +x ~/audit.sh, then run: sudo ~/audit.sh

Windows Investigation Commands

Quick Connection Snapshot

netstat -ano

What it shows: Protocol, local address, foreign address, state, PID.

Filter to established only:

netstat -ano | findstr ESTABLISHED

Map PID to Process Name

tasklist | findstr <PID>

Replace <PID> with number from netstat output.

PowerShell (Modern, Recommended)

Get-NetTCPConnection -State Established | Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,State,OwningProcess | Format-Table -AutoSize

Cleaner output than netstat, shows process IDs directly.

With Process Names (Color-Coded)

Get-NetTCPConnection -State Established | 
  ForEach-Object {
    $p = Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue
    $color = if ($_.RemoteAddress -match '^192\.168|10\.|172\.(1[6-9]|2[0-9]|3[0-1])\.') { 'Green' } else { 'Yellow' }
    Write-Host ("{0,-20} {1,-8} {2,-22} {3,-22}" -f $p.ProcessName, $_.OwningProcess, "$($_.LocalAddress):$($_.LocalPort)", "$($_.RemoteAddress):$($_.RemotePort)") -ForegroundColor $color
  }

GREEN = Local/private IPs | YELLOW = External/public IPs

Live Monitoring

netstat -b 5

Refreshes every 5 seconds with executable names. Press Ctrl+C to stop.

Local Network Discovery

arp -a

Shows IP ↔ MAC mappings for devices on your LAN.

Save Report

netstat -ano > %USERPROFILE%\Desktop\network_report.txt

Saves snapshot to Desktop for offline analysis.

Linux Investigation Commands

Modern Method (ss)

sudo ss -tunap

Flags: -t TCP, -u UDP, -n numeric, -a all, -p process

Filter to established:

sudo ss -tunap | grep ESTAB

Legacy Method (netstat)

sudo netstat -tunp | grep ESTABLISHED

Same information, older tool (present on most systems).

Full Connection List with Process Names

sudo lsof -i -nP

Works identically to macOS version (Linux has lsof too).

Watch Live Connections

watch -n 5 "ss -tunap | grep ESTAB"

Refreshes every 5 seconds. Press Ctrl+C to exit.

Local Network Scan

sudo nmap -sn 192.168.1.0/24

Requires nmap package. Replace subnet with your network range.

Android Investigation Methods

App-Based (No Root Required)

Recommended Apps:

  • Net Monitor (Evgeny Khardin): Shows active connections with hostname resolution
  • NetGuard: Creates local VPN to log all app connections (can block selectively)
  • Fing: Network scanner for LAN device discovery

Termux (Command-Line Shell)

Install Termux from F-Droid or Play Store, then:

pkg install net-tools procps

Check connections:

netstat -tunp

Clean formatted output:

netstat -tunp | awk 'NR>2 {printf "%-7s %-22s %-22s %-12s %-8s\n", $1, $4, $5, $6, $7}' | sed '1iPROTO   LOCAL_ADDRESS:PORT       REMOTE_ADDRESS:PORT      STATE        PID/PROGRAM'

Live Monitoring

watch -n 5 "netstat -tunp | grep ESTABLISHED"

Note: Android restricts visibility to processes owned by Termux session unless device is rooted. For full per-app visibility, use NetGuard.

iOS Investigation Methods

App-Based Solutions

iOS does not provide system shell access without jailbreak. Use these apps:

  • Fing: Network scanner, device discovery on LAN
  • iSH: Linux shell emulator (limited networking, but can run basic commands like arp -a)
  • Surge / Shadowrocket: Advanced network tools with connection logging (paid)

Remote SSH to Mac/Linux

If you SSH from iOS to a Mac/Linux machine (using Termius, Blink, or iSH), you can run full commands remotely:

ssh user@macbook.local 'sudo lsof -iTCP -sTCP:ESTABLISHED -n -P'

Network Analysis via Proxy

Configure iOS to route through a proxy (Charles, mitmproxy) running on desktop. This captures all HTTP/HTTPS traffic with full visibility into connections.

Best Practice: For sensitive work on iOS, assume limited visibility. Perform audits on desktop machines before/after mobile use.

Analysis: Reading the Output

Anatomy of a Connection Entry

Example (macOS lsof): Google 503 user 45u IPv4 0x123abc 0t0 TCP 192.168.1.5:52344->142.250.72.206:443 (ESTABLISHED) Example (Windows netstat): TCP 192.168.1.5:52344 142.250.72.206:443 ESTABLISHED 503 Example (Linux ss): tcp ESTAB 0 0 192.168.1.5:52344 142.250.72.206:443 users:(("chrome",pid=503))

Field Breakdown

Field Meaning What to Check
Process Name Application making connection Is this expected? Unknown processes = investigate
PID Process ID (unique number) Use to get more info: ps -p PID or Activity Monitor
Local Address:Port Your device's IP + ephemeral port Verify IP matches your interface (check ifconfig)
Remote Address:Port Destination IP + service port Critical: Who owns this IP? Where is it located?
State Connection status ESTABLISHED = active; LISTEN = waiting for inbound

Threat Assessment Framework

🟢 NORMAL — Expected Behavior

  • Browsers connecting to :443 (HTTPS) for known domains
  • Cloud sync apps (Dropbox, iCloud) to CDN IPs
  • OS update daemons to vendor servers
  • DNS queries to configured resolvers (:53)
  • Ephemeral ports (>1024) as local address

🟡 INVESTIGATE — Requires Verification

  • Unknown process names: Search online; check binary signature
  • Unexpected geographic locations: Use whois IP or MaxMind GeoIP
  • High connection frequency: 10+ connections to same IP may indicate data transfer
  • LISTEN states: Ensure you authorized these services (SSH, file sharing)
  • Connections to non-standard ports: Port 8080, 1337, etc. (could be proxies or malware)
  • Persistence: Same IP reappears across multiple audits

🔴 SUSPICIOUS — Immediate Action Required

  • Root/system process connecting externally: OS daemons shouldn't phone home unprompted
  • Connections to known-bad IPs: Check against threat intel feeds (VirusTotal, AbuseIPDB)
  • Obfuscated process names: Random strings, hidden files
  • Connections to Tor exit nodes or VPNs: Unless you're running them
  • Rapid port scanning: Many SYN_SENT states to sequential ports
  • Unusual protocols on standard ports: Non-HTTP traffic on :80/:443

IP Attribution Techniques

1. Reverse DNS Lookup

dig -x 142.250.72.206 +short
lga34s32-in-f14.1e100.net.

Reveals hostname (here: Google server in 1e100.net domain).

2. WHOIS Query

whois 142.250.72.206 | grep -E 'OrgName|CIDR|Country'
OrgName: Google LLC CIDR: 142.250.0.0/15 Country: US

Shows ownership, IP block, country of registration.

3. GeoIP Location

Use online tools (MaxMind, IPinfo.io) or command-line:

curl ipinfo.io/142.250.72.206
{ "ip": "142.250.72.206", "hostname": "lga34s32-in-f14.1e100.net", "city": "Mountain View", "region": "California", "country": "US", "org": "AS15169 Google LLC" }

4. Threat Intelligence

Check IP reputation:

  • VirusTotal: virustotal.com/gui/ip-address/[IP]
  • AbuseIPDB: abuseipdb.com/check/[IP]
  • AlienVault OTX: otx.alienvault.com/indicator/ip/[IP]

Case Studies (Anonymized)

Case 1: Persistent Unknown Connection

Observation: User noticed process named SystemUpdate (PID 1523) with persistent connection to 203.0.113.45:443.

Investigation:

  1. Check process path: ps -p 1523 -o comm= revealed binary in /tmp/.hidden/
  2. WHOIS lookup showed IP registered to bulletproof hosting provider in Eastern Europe
  3. VirusTotal: 12/70 AV vendors flagged IP as C2 server

Verdict: MALWARE

Response: Kill process, quarantine binary, full system scan, network forensics to identify entry vector.

Case 2: Cloud Service Telemetry

Observation: Legitimate app (Slack) connecting to 15+ different IPs in AWS ranges.

Investigation:

  1. Reverse DNS confirmed all IPs resolved to *.amazonaws.com
  2. Ports were :443 (HTTPS) and :5349 (TURN/STUN for WebRTC)
  3. Connection frequency aligned with app usage (spikes during calls)

Verdict: NORMAL

Note: Modern cloud apps use CDNs/load balancers, resulting in many IPs. Verify domain ownership, not just IP count.

Case 3: Open SSH Port

Observation: lsof showed sshd LISTEN *:22—SSH server listening on all interfaces.

Investigation:

  1. User confirmed never enabled Remote Login in System Preferences
  2. Checked sudo systemsetup -getremotelogin → returned "On"
  3. Reviewed /var/log/system.log for SSH authentication attempts—found 200+ failed logins from Chinese IP ranges

Verdict: EXPOSURE

Response: Disabled Remote Login, added firewall rule to block :22 from WAN, rotated passwords, enabled key-only auth.

Incident Response (Immediate)

When you confirm compromise.

  1. Isolate: Disconnect from network (Wi-Fi off, unplug Ethernet)
  2. Snapshot: Save full connection list, process list, open files
  3. Kill: Terminate malicious process (kill -9 [PID] or Task Manager)
  4. Block: Add firewall rule to prevent reconnection
  5. Preserve: Copy suspicious binaries to quarantine folder (don't execute)
  6. Scan: Run AV/malware scan (Malwarebytes, ClamAV)
  7. Review: Check persistence mechanisms (LaunchAgents, Startup folders, cron jobs)
  8. Rotate: Change passwords for all accounts accessed on compromised device
  9. Report: If work-related, notify IT/security team

Blocking Suspicious IPs

macOS (Packet Filter)

# Enable PF
sudo pfctl -e 2>/dev/null

# Create block rule
echo "block drop out quick on en0 from any to 203.0.113.45" | sudo tee /etc/pf.anchors/manual_block

# Load anchor
echo 'anchor "manual_block"' | sudo tee -a /etc/pf.conf
sudo pfctl -f /etc/pf.conf

# Verify
sudo pfctl -sr

# Remove block
sudo rm /etc/pf.anchors/manual_block
sudo pfctl -f /etc/pf.conf

Windows (Firewall)

# Block outbound to IP
netsh advfirewall firewall add rule name="BlockBadIP" dir=out action=block remoteip=203.0.113.45

# List rules
netsh advfirewall firewall show rule name=all

# Remove rule
netsh advfirewall firewall delete rule name="BlockBadIP"

Linux (iptables)

# Block outbound
sudo iptables -A OUTPUT -d 203.0.113.45 -j DROP

# List rules
sudo iptables -L -n -v

# Remove rule
sudo iptables -D OUTPUT -d 203.0.113.45 -j DROP

# Save permanently (Ubuntu/Debian)
sudo iptables-save > /etc/iptables/rules.v4

Establishing Baselines

Run weekly audits during normal operation. Compare snapshots to detect drift:

diff -u baseline_20251020.txt baseline_20251027.txt

New persistent connections = investigate. Disappeared services = verify expected.

Best Practices & Recommendations

General Security Hygiene

  • Minimize attack surface: Disable unused network services (file sharing, remote login)
  • Firewall by default: Enable OS firewall, default-deny inbound
  • DNS hygiene: Use trusted resolvers (1.1.1.1, 8.8.8.8) or encrypted DNS-over-HTTPS
  • VPN for sensitive work: Route through trusted VPN to obscure destination IPs from local network observers
  • Separate devices: Use dedicated machine for high-sensitivity work (air-gapped if possible)

Operational Protocols

  1. Pre-session audit: Always check connections before handling sensitive materials
  2. Post-session verification: Confirm no new persistent connections after closing sensitive apps
  3. Weekly baseline: Schedule recurring audits, save outputs, review diffs
  4. Document everything: Maintain audit log with timestamps, IPs, process names
  5. Threat intel integration: Subscribe to feeds (AlienVault OTX, Abuse.ch) and periodically check known-bad IPs

Recommended Tools

GUI Network Monitors

  • Little Snitch (macOS): Real-time connection alerts, per-app firewall rules
  • Radio Silence (macOS): Lightweight network monitor with blocking
  • GlassWire (Windows): Visual network activity, alerts on new connections
  • TCPView (Windows, Sysinternals): Free real-time connection viewer

Command-Line Power Tools

  • nmap: Network discovery, port scanning (install via Homebrew/apt)
  • tcpdump: Packet capture for deep inspection (requires expertise)
  • Wireshark: GUI packet analyzer (overkill for most, powerful for forensics)

Privacy Considerations

Legal Notice: Network monitoring of your own device is legal. Monitoring others' traffic without consent may violate wiretapping laws. Always operate within legal boundaries.

Operational Security:

  • Audit logs contain sensitive info (IPs you contacted). Encrypt stored reports.
  • Don't share raw lsof/netstat output publicly—it reveals your network topology.
  • When requesting help online, redact private IPs (192.168.x.x, 10.x.x.x).

When to Escalate

Seek professional assistance if:

  • You find connections to known C2 infrastructure
  • Processes resist termination or respawn immediately
  • Binary signature verification fails or shows unknown developer
  • You're handling materials that could endanger sources (journalists, researchers)
  • Organization policy requires formal incident response

Limitations & Context

Analytical Assumptions

This manual assumes an adversarial threat model—appropriate for researchers, journalists, activists, or anyone handling sensitive information. For casual users, the protocols here may be excessive. The goal is comprehensive visibility, not paranoia.

Technical Limitations

  • Encrypted traffic: These tools show where you connect, not what you send. HTTPS/TLS hides content.
  • VPN obfuscation: If using VPN, all remote IPs appear as VPN server. Pre-VPN audit required.
  • Rootkits: Advanced malware can hide from lsof/netstat. Kernel-level inspection needed.
  • Mobile restrictions: iOS/Android limit system visibility—app-based solutions are proxies, not full audits.

Skill Requirements

Interpreting network data requires baseline technical literacy:

  • Understanding IP addressing (IPv4/IPv6)
  • Familiarity with common ports/protocols
  • Ability to research unfamiliar process names
  • Comfort with command-line interfaces

If these are unfamiliar, start with GUI tools (Little Snitch, NetGuard) before diving into terminal commands.

Ethical Considerations

Network monitoring is a defensive practice. Misuse—monitoring others without consent, using tools for reconnaissance on third-party networks—crosses legal and ethical lines. This manual is for securing your own devices, not surveilling others.

Platform Bias

Command examples prioritize Unix-like systems (macOS, Linux) due to richer built-in tooling. Windows coverage is functional but less granular. Mobile platforms (iOS, Android) receive less depth due to OS restrictions. For enterprise Windows environments, consider SIEM tools (Splunk, ELK) for centralized monitoring.

Currency

Network tools and threat landscape evolve constantly. This manual reflects best practices as of October 2025. Tool syntax may change; new vulnerabilities will emerge. Treat this as a conceptual foundation, not immutable scripture.
